## 0. Summary

1. **compiler-rt's own builtins work for MSIL as a static CIL archive, today, without a compiler change.** 142 of 176
   builtins sources compile for `x86_64-unknown-linux-gnu-msil` (with `-D__ELF__`), 155 for `x86_64-pc-windows-msvc-msil`,
   156 for `aarch64-unknown-linux-gnu-msil` (E1). Linked by msil-ld from an `llvm-ar` archive, a program using complex
   multiply/divide (Annex G cases included), `_Float16` arithmetic and conversions, `powi` and 128-bit overflow builtins
   prints output **bit-identical to the native builds** on .NET 8, .NET 10, .NET Framework 4.8, WSL .NET 8 and .NET 10, the
   native Windows build (compiler-rt) and the native Linux build (libgcc_s) (E2). The clang driver already passes
   `<resource-dir>/lib/<msil-triple>/{clang_rt.builtins.lib|libclang_rt.builtins.a}` to msil-ld when it exists
   (`clang/lib/Driver/ToolChains/MSIL.cpp:248-253`; verified with `-resource-dir`, E6). LTO links pull codegen-created
   helper calls from the CIL archive after LTO (E5). Helpers stay private: they become methods of `<Module>`, and with
   compiler-rt's default `-fvisibility=hidden` a `-shared` library does not export them (E7).
2. **Three defects block or endanger that path** (all small): (a) bf16 helpers cannot link: a defined function returning
   `__bf16` gets the IL signature `float32(...)` (through an `__extendbfsf2` call), while the legalizer's libcall expects
   `int32(...)`, so `__truncsfbf2`/`__truncdfbf2` are `function signature mismatch` errors (E3); bf16 must be passed as its
   bits in `int32`, as f16 already is. (b) **msil-ld silently binds compiler-rt helper names to a native library**:
   linked against `libgcc_s.so.1`, `__extendhfsf2`/`__truncsfhf2` became P/Invokes and returned garbage (`0x0000` instead
   of `0x3E00`), because the libcall's call-site signature (`int32(float32)`) hides the `half` that would mark it
   NATIVE_INCOMPATIBLE (E4). msil-ld must never bind a `__`-prefixed RuntimeLibcalls name natively. (c) The
   `__ELF__`-less Linux MSIL triples hit `compiler-rt/lib/builtins/int_lib.h:70` (`#error Unsupported target`) (E1).
3. **Helper delivery recommendation: C helpers in a per-triple `clang_rt.builtins` CIL archive** built from compiler-rt
   (plus a small `msil/` subdirectory of MSIL-specific C helpers) for the compiler-rt families (f16/bf16, complex, powi,
   i128 division and conversions, constrained FP<->i128, `__cpu_model`, odd-size atomics); **IL helpers generated by the
   toolchain** (the M20 trailer builder pattern: `cli::ILBuilder` + `TrailerSink`, shared by `-S` and msil-ld) for runtime
   services that need .NET types (TLS block, shadow stack, atexit/ProcessExit hook, setjmp exception class, thunk table,
   bit-cast union type); **no bitcode helper archive**: msil-ld (like every lld port) extracts every bitcode member that
   defines a RuntimeLibcalls name into every LTO link (`__extendhfsf2` and `__truncsfhf2` were pulled into a program that
   uses neither, E5), while a CIL archive pulls nothing. IR-level `linkonce_odr hidden` COMDAT helpers deduplicate across
   CIL objects (one copy, E11) and remain the tool for helpers `-S` must contain.
4. **Codegen switch recommendation: MSIL target features** (`-mmsil-<name>` -> `-target-feature +msil-<name>` ->
   per-function `"target-features"`), the WebAssembly model this target already follows. Per-function attributes give the
   same API choice per translation unit in object and LTO links; module flags cannot (measured merge rules: `Min` turns a
   flag missing in one module into 0, `Max` takes the maximum, `Error` stops the link, E10). The capability check against
   the references is M21's *optional substitute* request carried in the reserved `MANAGED_REQUESTS` subsection (record
   v1.1): msil-ld rewrites each call token to the BCL member when a reference defines it and to the fallback helper
   symbol otherwise. LTO needs no separate path (LTO output is a CIL object), and `-S` text always uses the fallback.
5. **BCL intrinsics pay off** (.NET 8, TieredCompilation=0, E13/E14): BitOperations.PopCount 3.6x faster than today's
   30-instruction expansion, LeadingZeroCount 7.4x, ReverseEndianness 2.8x, RotateLeft 1.0x (the JIT already recognizes
   the rotate idiom); Math.Floor 3.2x and Math.Sqrt 3.7x faster than today's libm P/Invokes (7.2x and 13.3x on .NET
   Framework), and a P/Invoke call site costs about 210-240 bytes of JIT code against 4-10 bytes for the Math call.
   Several of the winners are **in mscorlib and exact on every runtime** (Math.Sqrt, Floor, Truncate, Round(x),
   Round(x, AwayFromZero), Abs, BitConverter.DoubleToInt64Bits): measured bit-identical to UCRT and glibc on all eight
   configurations for the edge inputs tried, **except Math.Ceiling, which loses the sign of zero on .NET Framework
   (`ceil(-0.5)` = +0)**, so ceil must be `-Math.Floor(-x)`. These need no switch under the user's rules (they run on
   Framework 4.8 and modern .NET alike) but change D14/D16's defaults: a user decision.
6. **libm:** on modern .NET, `Math.Sin`/`Cos`/`Tan`/`Exp`/`Log`/`Pow`/... are bit-identical to the host libm (UCRT on
   Windows, glibc under WSL) for every input tried, apart from the sign of some NaNs; on **.NET Framework they are wrong
   for large arguments** (`Math.Sin(1e22)` returns 1e22, `Math.Tan(1e22)` NaN, `Math.Pow(1, NaN)` NaN, `Math.Exp(-745.13)`
   0 instead of the smallest subnormal). Mapping saves little time (`sin` 15.5 -> 14.3 ns). With `-fmath-errno` (the
   Linux default) clang never produces the intrinsics, so errno semantics are safe by construction. Recommendation: keep
   the host-libc P/Invokes (D14) by default; an optional `-mmsil-bcl-math` switch for errno-free intrinsics, gated on
   references that exclude .NET Framework.
7. **Architecture intrinsics:** `pause` -> `Thread.SpinWait(1)` (mscorlib; 54-96 ns against 40-45 ns for one real `pause`),
   fences -> `Interlocked.MemoryBarrier` (D36's call), `crc32` -> a C helper (table CRC32C, 9-19 ns per u32, exact against
   `Sse42.Crc32`'s 0.7-2.3 ns), MSVC `__fastfail` (clang builtin and Rust's `int $$0x29` asm) -> `Environment.FailFast`
   (exit status 0x80131623 against native 0xC0000409), `__builtin_cpu_supports` -> a `__cpu_model` helper reporting no
   features; System.Runtime.Intrinsics only behind `-mmsil-x86-intrinsics` with an `IsSupported` guard and the same
   fallback. SkipLocalsInit needs no switch: our methods never set `localsinit`, and localloc'd frames are already not
   zeroed on all three runtimes (E12). DisableRuntimeMarshalling changed nothing measurable for our blittable P/Invokes;
   SuppressGCTransition cut a libm P/Invoke by about 35 percent (E15) but is unsafe for blocking or calling-back
   functions, so it belongs to a per-declaration attribute, not a global switch.

## 2. Private helpers

### 2.1 The three options

**(A) IL helpers generated by the toolchain.** C++ in `llvm/lib/CLI` (a helper library beside `Trailer.cpp`) emitting
`cli::ILBuilder` bodies through `TrailerSink`, so `-S` (text sink) and msil-ld (row sink) share one implementation (Q5's
rule). msil-ld synthesizes a helper when an object references its symbol or when a feature needs it (like
`'<msil>dataimport'`), so each output has one private copy. Can do what C cannot: define classes and fields
(`[ThreadStatic]`, explicit-layout value types, an exception class), exception filters, delegates, BCL calls with
references chosen at link time. Cost: every helper is hand-written IL in C++; tests are yaml2obj/lld lit tests plus
runtime transcripts. Right for runtime services, wrong for numeric code (hundreds of IL instructions by hand).

**(B) C helpers compiled by this toolchain into a static archive, linked like compiler-rt builtins.** Build: compile
`compiler-rt/lib/builtins` (plus an MSIL subdirectory) with clang for each MSIL triple into CIL objects, `llvm-ar` them,
install into `lib/clang/<ver>/lib/<msil-triple>/`. Measured to work end to end (2.2). Cost: a build step per MSIL triple,
a source list for MSIL, two small source guards. Free correctness: compiler-rt's code is the native reference
implementation, so results equal native compiler-rt bit for bit (E2).

**(C) Helpers in LLVM IR.** Two forms. (C1) a bitcode archive: **rejected by measurement** (E5): msil-ld's LTO, like
lld/ELF and lld/wasm, extracts every lazy bitcode member that defines a RuntimeLibcalls name before LTO
(`lld/MSIL/Driver.cpp:1570-1578`), so `__extendhfsf2` and `__truncsfhf2` joined a program that uses neither (row of
2026-10-22 on 5.9.13 describes the hazards: constructors, duplicate and undefined symbols); helpers would also be LTO'd
into every link. (C2) IR functions generated per module by the backend (MSILPrepareIR) as `linkonce_odr hidden` in a
COMDAT: msil-ld keeps one copy (E11: two objects each defining `__msil_popcount32` give one method, correct result), and
`-S` text contains them. Right for out-of-line copies of big expansions that `-S` must keep runnable (backlog 2.2's
i128 outlining), not as the general delivery.

### 2.4 bf16 cannot link today (E3)

With the bf16 sources in the archive: `msil-ld: error: function signature mismatch: __truncsfbf2 >>> defined as
float32(float32) in clang_rt.builtins-win.lib(truncsfbf2.c.o) >>> called as int32(float32) in helpers-win.o` (same for
`__truncdfbf2`). A *defined* function returning `__bf16` lowers its return through `__extendbfsf2` to `float32` (and in
`-S` mode `truncsfbf2.c` itself fails with `runtime helper '__extendbfsf2' is not available for MSIL yet (phase 3)`),
while `LowerBF16Conversion` (`MSILISelLowering.cpp:1179-1209`) calls the helper with the soft-promoted `int32`. f16
already uses `int32` for both (`__truncsfhf2` is `int32(float32)` in both places). Fix: map `bf16` in signatures to its
16-bit pattern in `int32`, as for `f16` (the native x86-64 ABI passes both in XMM registers as 16-bit patterns, so neither
is P/Invoke-compatible anyway). Objects with bf16 signatures cannot link today, so the change breaks nothing.

### 2.5 Native binding of helper names (E4)

Linked with `libgcc_s.so.1` (on Linux it exports `__muldc3`, `__divdc3`, `__mulsc3`, `__powidf2`, `__extendhfsf2`,
`__truncsfhf2`, `__truncdfhf2`, `__extendbfsf2`, `__truncsfbf2`), msil-ld refused the complex helpers (`takes or returns a
value that a P/Invoke cannot pass natively yet`) but bound the f16 ones as P/Invokes without a word:
`.pinvokeimpl 'libgcc_s.so.1' entry '__extendhfsf2'`. Under WSL .NET 8 `(_Float16)1.5f` gave `0x0000` and `2 * h` gave
`0x39E60000`; with the CIL archive, `0x3E00` and `0x40400000`. The record's call-site signature of a DAG libcall is
already soft-promoted (`int32(float32)`), so NATIVE_INCOMPATIBLE (5.8.8) cannot catch it. The default link does not pass
`-lgcc_s` (the Linux MSIL driver passes `-lc -lm` only), and archives already win over native libraries whatever the
command-line order (libgcc_s first, then the archive: only `puts` was a P/Invoke), but a user `-lgcc_s` or a library that
exports such a name is enough. **Rule for msil-ld:** a symbol in `lto::LTO::getRuntimeLibcallSymbols(target)` whose name
starts with `__` never binds to a native library; unresolved, it is `undefined symbol: <name> (a compiler runtime helper;
link the toolchain's helper archive clang_rt.builtins)`.

**Privacy.** Archive members compile with `-fvisibility=hidden` (compiler-rt's `COMPILER_RT_BUILTINS_HIDE_SYMBOLS`,
default ON), so a `-shared` link never exports them (E7: `lib1.dll`'s symbol table lists only `lib_cmul` and `lib_h`;
`__muldc3` and `__truncsfhf2` are `<Module>` methods with flags 0x0016, and `<Module>` is not public). Each assembly gets
its own copy, so two libraries never share or clash on a helper (5.9.15's duplicate-definition warning concerns exported
symbols only). IL helpers are `assembly`-private methods of `<Module>` or private classes, as `'<msil>SymbolTable'` is.
One caveat for the end-of-project multi-triple assembly idea: helpers of two triples in one `<Module>` would collide by
name, so such an assembly would need a per-triple holder class; nothing here precludes that.

**`-S` and llc.** They link nothing, so archive helpers stay errors there (reworded to name msil-ld and the archive);
IL service helpers are printed through `MSILTrailerTextSink`, so `-S` output stays runnable for TLS, atexit and setjmp.

**Testing.** compiler-rt's own `compiler-rt/test/builtins/Unit` has 238 tests, 224 of which call `printf` (a native
variadic call, possible only after P3-B); until then, transcript tests in `msil/test` against the native oracles
(`helpers.c` is a template), plus `lld/test/MSIL` tests for the native-binding refusal and the request rewriting.
Stale archives after an ABI change are caught by the link-info ABIVersion equality check (5.8.9).

### 2.7 i128 division through the helper (E9)

3,000,000 u128 divisions (recon/p2 `bench.c`), whole process, loaded host: inline (M12) 6,576 ms on .NET 8 and 4,866 ms
on Framework; `__udivti3`/`__udivmodti4` from compiler-rt (generic path) 5,872 ms and 4,988 ms; native 1,208 ms; the
unloaded numbers of the Phase 2 recon were 1,023 ms (inline, .NET 8), about 300 ms (native) and 428-482 ms (C# UInt128).
So the helper is a **size** win (one copy per assembly instead of 881-1,053 IL instructions per division function) at
equal speed; `Int128`/`UInt128` (net7+) would be the speed win, behind a switch.

## 3. Codegen switches

### 3.1 Carrier: where a switch lives

| Carrier | Per TU under LTO | Inlining across TUs | Front-end plumbing | Precedent |
|---|---|---|---|---|
| **(a) target features `+msil-<name>`** in `"target-features"` | kept per function | default TTI blocks unequal feature strings; MSIL TTI overrides `areInlineCompatible` to compare only native features | `handleTargetFeaturesGroup` for an `m_msil_Features_Group` (one call in `tools::getTargetFeatures`, `clang/lib/Driver/ToolChains/CommonArgs.cpp:885-890` shows wasm's); `MSILTargetInfo` accepts `msil-*` names and defines `__MSIL_<NAME>__`; `__attribute__((target("msil-bitops")))` works | WebAssembly: `-mbulk-memory` -> `+bulk-memory` per function, `WebAssemblyCoalesceFeaturesAndStripAtomics`, `target_features` section, wasm-ld `--features`/`--extra-features` (`lld/wasm/Writer.cpp:597-640`) |
| (b) a separate string attribute `"msil-switches"` | kept per function | not checked by default | new CodeGenOptions, cc1 options and attribute emission | none |
| (c) module flags | merged: `Min` makes a flag absent in one module 0, `Max` takes the maximum, `Error` stops the link on unequal values (E10, measured through msil-ld LTO) | n/a | clang `CodeGenModule` flags | `wchar_size` (Error), PIC Level |
| (d) TargetOptions / `cl::opt` | lost in bitcode | n/a | `-mllvm` | debugging only |

Module flags cannot keep an object link and an LTO link of the same TUs equivalent: with `Min`, one TU without the switch
turns it off for the whole LTO module; with `Max`, one TU turns it on for code compiled without it. Per-function
attributes give the same API choice per function in both pipelines. **Recommendation: (a).** Because every switch-gated
lowering implements the *same* LLVM operation exactly (3.4), inlining a callee into a caller with other switches only
changes which API implements the operation, never its result, so the TTI override may allow it.

`MSIL::filterMSILFeatures` keeps `msil-*` features and drops native ones before `ParseSubtargetFeatures`; `MSIL.td`
gains one `SubtargetFeature` per switch and `MSILSubtarget` predicates (`HasBitOps`, ...) gate TableGen patterns.
`MSILTargetMachine::getSubtargetImpl(const Function &)` needs no change (it already keys on the full feature string).

### 3.2 The reference check (capability from the references)

- **Objects.** A switch-gated lowering emits a call to the BCL member (a `BCLMembers.def` row with strength
  `OptionalSubstitute` and a fallback symbol) and records the request in `MANAGED_REQUESTS` (record **v1.1**: subsection
  0x08 below `FirstOptional`, so an older msil-ld refuses such an object instead of misreading it): per request the
  MemberRef token, the strength, the fallback symbol and the switch name. msil-ld binds the member when some reference
  defines it; otherwise it **rewrites the call's token** to the fallback symbol's method (it already decodes and
  renumbers every token, M20) and reports `note: '<member>' is not defined by the references; using helper '<symbol>'
  (requested by <file> for <switch>)` under `--verbose` (Q11's text). A private thunk (5.11.5's wording) is needed only
  when the IL stack types of member and fallback differ; `uint32` vs `int32` do not (both are int32 on the stack:
  `BitOperations::PopCount(uint32)` and compiler-rt's `int __popcountsi2(int)` are interchangeable).
- **LTO.** msil-ld's LTO writes a CIL object (`*.lto.o`) and links it like the others, so the same requests work; no
  module flag is needed (the 5.11.5 remark "the capability may later reach codegen as a module flag" can stay unused).
- **`-S`, llc.** No references: the backend emits the fallback directly (the built-in `[mscorlib]` table holds none of
  the switch-gated members).
- **Attributes** (`DisableRuntimeMarshalling`, `SuppressGCTransition`) are `OptionalDrop` (Q11).
- **Behaviour that a member's presence does not reveal.** `Math.Min`/`Max` exist in mscorlib on .NET Framework with other
  signed-zero semantics (measured: `Math.Min(-0.0, +0.0)` is +0 on Framework, -0 on .NET 8/10), and Framework's
  `Math.Sin`/`Pow` differ from C (section 6). Such a request carries a **probe member** that appeared with the behaviour
  (`Math::MaxMagnitude` for the IEEE 754-2019 min/max change, believed to be .NET Core 3.0: *unverified*, only 6-10 are
  installed), and binds only when the probe binds too. This keeps D16's rule (the switch alone may not decide) while
  using the existing binder.
- **msil-ld's own synthesized code** (TLS allocation, data imports): M21 already lets `'<msil>dataimport'` use
  `NativeLibrary` exactly when the references define it, with no switch. For identical-result choices (NativeMemory vs
  AllocHGlobal) this rule can extend; it is listed as a decision because the user's rule names switches.

### 3.3 Spelling, defaults, record bits

- clang: `-mmsil-<name>` / `-mno-msil-<name>` (target-specific `-m` group, like `-msimd128`; the `msil-` prefix keeps them
  apart from native features such as `-mpopcnt`, and from the rejected `-mdotnet` profile). Rejected on non-MSIL triples
  with `unsupported option for target`.
- Link-time switches (assembly attributes, thunk shape): msil-ld options `--disable-runtime-marshalling`,
  `--unmanaged-callers-only`; the driver forwards `-mmsil-disable-runtime-marshalling` etc. when it links.
- Link-info: one `FeatureFlags` bit per codegen switch an object's functions use (OR'd by msil-ld, printed by
  `llvm-cil-dump --link-info` and `--verbose`); no switch in the initial list changes the ABI (f16 and i128 keep their
  current signature representation; `System.Half`/`Int128` are used only inside lowerings), so `ABIFlags` stay 0.
- Defaults: **every switch off on every triple.** Linux triples cannot run on .NET Framework, but whether the BCL member
  is used is decided by the references anyway, and identical defaults keep the test matrix one-dimensional.
- Native target features (`-mavx2`, `-msse4.2`) keep their native meaning (macros, which intrinsics compile, the
  vectorizer); they never enable a .NET API. An x86 intrinsic maps to `System.Runtime.Intrinsics.X86` only under
  `-mmsil-x86-intrinsics`, guarded by `IsSupported`; full SIMD (`Vector128`, AVX) is a later `msil-simd` feature (phase 4).

### 4.3 Exact substitutions available everywhere (no switch)

must pass `msil/utils/check-mscorlib-safe.py`; before committing, a property test (10^7 random doubles plus all special
classes, every runtime) should replace this recon's 15-input probe.

## 5. libm

- **Today (D14):** every math library function is a host-libc P/Invoke (`libm.so.6`, `ucrtbase.dll`); LLVM's FP intrinsics
  are libcalls to the same functions.
- **errno decides which calls can move.** With `-fmath-errno`, the Linux default, clang emits `call @sin`, `@sqrt`, `@log`
  with `memory(errnomem: write)` and only `floor`, `fmin` as intrinsics; with `-fno-math-errno` (the MSVC default, or
  explicit) it emits `llvm.sin`, `llvm.sqrt`, `llvm.log`. So a backend mapping of the *intrinsics* (ISD nodes) never
  changes errno behaviour; calls stay P/Invokes.
- **Measured** (`helpers-switches-files/libm/fp-diff.md`; 369 values of `fpprobe.c`/`fpprobe-Program.cs`, 55 differ somewhere):
  - modern .NET on Windows equals UCRT and modern .NET under WSL equals glibc for sin, cos, tan, exp, log, log10, atan,
    sinh, tanh, asin, acos, pow, atan2, cbrt and MathF sin/exp/pow on every input tried, except NaN signs: glibc
    `log(-745.13)` and `log(-1)` give -NaN, .NET on Linux +NaN; CIL `rem` (C# `%`) of `(0,0)`, `(1,0)`, `(inf,2)` gives
    -NaN on Windows .NET 8 and Framework but +NaN on .NET 10 (UCRT fmod: +NaN; glibc: -NaN); `Math.IEEERemainder` gives -NaN
    where C `remainder` gives +NaN.
  - UCRT and glibc differ from each other in the last bit for `tan(1e22)`, `log10(pi)`, `atan(pi)`, `sinh(pi)`, `sinh(2)`,
    `sin(pi/4)`, `cos(pi/2 + 1ulp)` and `cbrt(27)` (glibc 3.0000000000000004), so "Math instead of libm" already means
    "this OS's libm" on modern .NET.
  - **.NET Framework 4.8** (x87 code paths): `Math.Sin(1e22)` and `Math.Cos(1e22)` return 1e22, `Math.Tan(1e22)` NaN,
    `sin/cos(1e300)` garbage, `cos(pi/2)` = 0x3c91a60000000000 (truncated reduction), `Math.Pow(-1, inf)`, `Pow(1, NaN)`,
    `Pow(NaN, 0)` NaN (C: 1), `Math.Exp(-745.133)` 0 (C: 4.9e-324), `Math.Min(-0, +0)` +0, `Math.Ceiling(-0.5)` +0; no
    MathF, Cbrt, FusedMultiplyAdd, CopySign, ScaleB, Log2, BitDecrement.
  - `fmin/fmax` vs `Math.Min/Max`: C ignores a NaN operand (`fmin(NaN, 1)` = 1), Math propagates it on every runtime;
    signed zeros: UCRT `fmin(-0,+0)` = -0, glibc +0, Framework `Math.Min` +0, .NET 8/10 `Math.Min` -0 in both orders.
- **Options:** (L1) keep P/Invokes everywhere; (L2) one switch `msil-bcl-math` mapping errno-free intrinsics to Math/MathF
  when the references exclude Framework (probe); (L3) per-function switches; (L4) map by default. Recommendation: **L1
  default, L2 as an optional switch**; never map on Framework (measured wrong results), never map calls (errno), keep
  sincos split (MSILISelLowering's FSINCOS rule). The exact operations of 4.3 are not "libm" in this sense.

### 6.1 Inventory

  `llvm.x86.sse42.crc32.32.8/32.32/64.64`, `llvm.x86.rdtsc`, `llvm.x86.rdtscp`, `llvm.x86.sse2.mfence/lfence`,

- `arch/sse2.c`: SSE2 is the x86-64 baseline (`__SSE2__` is predefined), so `#ifdef __SSE2__` paths are live, and six

  `pslli.d` (variable count); loads, compares, logic, shuffles and byte shifts are generic IR.

**Dead dispatch paths.** Code like `if (__builtin_cpu_supports("sse4.2")) crc_hw(); else crc_sw();`, with `crc_hw` in a
function carrying `__attribute__((target("sse4.2")))`, never runs `crc_hw` once `__cpu_model` reports no features, but
its intrinsics still fail to compile. Two policies: give every such intrinsic a fallback (the table), or lower an
intrinsic without one to `throw PlatformNotSupportedException` (Design.md 3.2's managed analogue of `#UD`) with a
warning, *only* in functions whose `target-features` exceed the translation unit's baseline (they are reachable only
after a runtime check). Recommendation: the fallbacks above now, the PNSE lowering as an explicit option
(`-mmsil-unsupported-intrinsics=error|throw`, default `error`).

The rewrites belong in MSILPrepareIR before its target-intrinsic check (`MSILPrepareIR.cpp:1226`); a BCL call from IR
needs one generic mechanism, a declaration attribute such as `"msil-bcl"="Thread_SpinWait"` naming a `BCLMembers.def`
row that `LowerCall` emits as `call [msil.bcl]...` (the M13 import-attribute pattern). That mechanism is also the seed of
the managed-calls goal (section 7).

## 7. Late goals: what Phase 3's choices ease or preclude

- **Portable triple `msil64-unknown-dotnet`:** the per-triple archive is triple-agnostic; it needs the `__MSIL__` alias
  branch in `int_lib.h` (2.3 item 2; neither `__ELF__` nor `_WIN32` will hold) and its own MSIL source list (no x86
  fallbacks). `msil-bcl-math`'s Math mapping is the natural libm for a portable libc, and compiler-rt's
  `COMPILER_RT_USE_LIBC_MATH` (builtins over LLVM libc's shared math, `compiler-rt/lib/builtins/CMakeLists.txt`) is a
  ready link between the two projects. x86/ARM intrinsic switches do not apply to an AnyCPU triple; the generic ones
  (bitops, fma, int128, minmax) do. Nothing precludes it; keeping switch names architecture-free except the
  `*-intrinsics` ones helps.
- **Managed calls from C:** the IR-level BCL call attribute (6.2) plus `OptionalSubstitute` requests are a small subset of
  "C calls a .NET member bound by msil-ld"; designing that attribute as "member named by the binder" eases the goal.
- **Inline IL:** BCL calls already go through `MSILMemberRefExpr::createBCL`; inline IL's `call` operands can reuse it.
  Nothing here precludes it.
- **FeatureIdeas (multi-triple assemblies):** helpers named in `<Module>` would collide between triples; a per-triple
  holder class later solves it (2.6). Not precluded.
- **Final cleanup:** the diagnostics that say "(phase 3)" are listed in 1.1.

## 8. Decisions

**H1. How are helpers delivered?** Options: (a) IL helpers only; (b) a C helper archive (compiler-rt builtins per MSIL
triple) for compiler-rt families plus toolchain-generated IL for runtime services; (c) a bitcode helper archive.
Recommended: **(b)**, with IR `linkonce_odr` COMDAT helpers only where `-S` needs a body. Evidence: E1/E2 (bit-identical
to native on 7 configurations), E5 (bitcode members extracted into every LTO link), E11 (COMDAT dedup), E7 (privacy).

**H2. How is the archive built?** Options: (a) teach compiler-rt's CMake about MSIL triples and build through
`LLVM_BUILTIN_TARGETS` in the main build; (b) a tracked script (`msil/utils/build/build-builtins.py`) that runs the
standalone `compiler-rt/lib/builtins` CMake per MSIL triple into the resource dir of a given build; (c) a script that
compiles a source list directly with the built clang. Recommended: **(a)'s compiler-rt changes as the single source list,
used through (b) for development, gates and CI** (no reconfiguration of the shared build; standard layout for later
releases). Evidence: E8 (stock CMake configures and builds once the list excludes 34 sources; 262 s + 78 s per triple
loaded), 2.3, E6 (driver already looks up the per-target path).

**H3. Native binding of compiler-rt helper names.** Options: (a) keep today's behaviour; (b) msil-ld never binds a
`__`-prefixed RuntimeLibcalls name natively. Recommended **(b)**. Evidence: E4 (silent wrong results via libgcc_s).

**H4. bf16 in signatures.** Recommended: pass bf16 as its bits in `int32`, like f16. Evidence: E3.

**H5. i128 division.** Options: keep M12's inline expansion; use the archive's `__divti3` family in objects and LTO (inline
stays in `-S`); `Int128` behind `msil-int128`. Recommended: helper in objects/LTO (size), switch for speed. Evidence: E9,
recon/p2 backlog 2.2.

**S1. Switch carrier.** Options: MSIL target features; a separate function attribute; module flags; TargetOptions.
Recommended: **MSIL target features (`+msil-<name>`)** with an MSIL `areInlineCompatible` that ignores them. Evidence:
E10, the WebAssembly precedent (3.1).

**S2. Switch spelling** (user-visible). Options: `-mmsil-<name>`; `-fmsil-<name>`; `-mdotnet-<name>` (too close to the
rejected profile). Recommended: **`-mmsil-<name>`/`-mno-msil-<name>`** for codegen switches and msil-ld `--<name>`
forwarded by the driver for link-time ones.

**S3. Reference check.** Recommended: `MANAGED_REQUESTS` in record v1.1, `OptionalSubstitute` with a fallback symbol,
token rewriting by msil-ld, a probe member for behaviour that presence cannot reveal, `-S` always the fallback, LTO
through the same objects. Evidence: 3.2, M21's binder.

**S4. Initial switch list and defaults.** Recommended: `msil-bitops`, `msil-fma`, `msil-minmax`, `msil-int128`,
`msil-x86-intrinsics`/`msil-arm-intrinsics`, `--disable-runtime-marshalling`, `--unmanaged-callers-only` (P3-B); all
**off on every triple**; `msil-bcl-math` and `msil-half` second wave; SuppressGCTransition later as a per-declaration
attribute; no SkipLocalsInit. Evidence: 3.5, E12-E15.

**S5. Exact mscorlib-safe substitutions without a switch.** Options: (a) keep D14/D16 (libm P/Invokes, localloc
bitcasts); (b) map sqrt, floor, ceil (as `-Floor(-x)`), trunc, rint, nearbyint, roundeven, round, fabs to `Math` and the
bitcasts to `BitConverter`/a union type by default. Recommended **(b)**, after a property test on every runtime. Evidence:
4.2-4.4 (3-13x faster, 200+ bytes less code per site, bit-identical; Math.Ceiling's Framework defect shows why each
member needs the test).

**S6. API choice in msil-ld's own synthesized code by references alone** (NativeMemory vs AllocHGlobal, like M21's
NativeLibrary). Recommended: yes, for identical-result choices only. Evidence: M21 precedent.

**L1. libm to Math/MathF.** Recommended: keep the host-libc P/Invokes by default; optional `msil-bcl-math` for errno-free
intrinsics gated on references that exclude .NET Framework. Evidence: section 5.

**A1. Architecture intrinsics.** Recommended: default fallbacks of 6.2 (pause, fences, clflush, crc32, bextr, fastfail,
cpu_model); System.Runtime.Intrinsics only behind `msil-x86-intrinsics` with `IsSupported` guards; rdrand stays an error;
PNSE lowering of dead-path intrinsics only on request. Evidence: 6.1-6.2, E17, E18.

**A2. rdtsc.** Options: keep the error; a monotonic-counter helper (QPC / `clock_gettime`). Recommended: the helper, with
the deviation documented (benchmarks such as timing loops then build). Needs the user: it changes a value's meaning.

## 10. Risks

- A new build step (the archive) in every gate and CI job; a stale archive links until an ABIVersion bump catches it.
- compiler-rt edits are upstream-file edits (fork maintenance); keep them to the source list and two guards.
- "Exact" BCL members can still differ by runtime (Framework `Math.Ceiling`); each mapped member needs the property test.
- Token rewriting assumes stack-compatible signatures between member and fallback; a mismatch needs the thunk.
- Timing numbers come from a loaded host (ratios are reliable within a run).
- PNSE lowering, if adopted, can hide a real portability bug behind a runtime exception.
